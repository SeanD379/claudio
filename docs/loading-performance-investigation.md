## 运行诊断如何使用

1. 打开本地预览，打开开发者工具 Console 和 Network，然后复现慢加载或失败。
2. 每次播放的 `X-Request-ID` 与浏览器 `[loading]` 日志中的 `requestId` 相同。在服务日志或 Netlify Functions 日志里搜索此 ID 即可串联。
3. 浏览器控制台执行 `window.claudioLoadingDiagnostics.snapshot()` 查看记录；执行 `copy(window.claudioLoadingDiagnostics.exportJSON())` 复制 JSON，保存到 `D:/CodexData/outputs/claudio/`。`copy` 是开发者工具辅助方法。执行 `.clear()` 可清空当前页面记录。
4. 浏览器仅保留本页面最近 200 条记录，不写 localStorage，不自动上传；刷新后清空。请在刷新前导出。服务端使用既有 stdout / Netlify 日志，不依赖函数文件系统持久化。
5. 在本文件追加对应问题编号、导出文件名、关联 ID、复现环境和复测结论。没有证据的原因标为“待验证”。

每条日志包含 `time/requestId/songId/stage/elapsedMs/result`，按需要附加 `errorCategory/status/size`。不包含 Cookie、Token、账号资料、歌曲名称或完整图片/音频地址。封面每个实例使用独立关联 ID，可用歌曲 ID 与播放记录对应；歌单拼图可能没有歌曲 ID。

### 阶段与计时边界

- 播放：`click → feedback-state → before-play（若有）→ url-request → url-ready → source-set → playing`；已有音源时省略请求阶段。`buffering/resumed/stalled/paused/ended/failure/superseded` 记录后续情况。
- `feedback-state` 表示同步更新状态，**不是已绘制到屏幕**；`playing` 是浏览器开始播放的事件，不能证明扬声器实际发声。
- 服务端：`credentials-ready → upstream-ready → song-url-response`，`elapsedMs` 都是自接口收到请求起的累计耗时；相邻阶段相减可估算该段耗时。上游阶段包含 SDK 准备和上游请求，尚不能拆分 DNS/TLS/网易云处理。
- 封面：`cover-mounted → cover-visible`，后者是加载事件，包含懒加载排队等待和下载，**不是单独网络耗时或已绘制耗时**。不把跨域 Resource Timing 的缺失数据当作零耗时。
- 等待 3 秒显示慢加载提示；播放前置逻辑结束后，每段起播/缓冲等待上限 15 秒，超时停止并允许重试或切歌。地址接口最长等待 12 秒。主动切歌记录为取消，不计为故障。
- 本地取消会中止到 3001 的 HTTP 等待；第三方 SDK 未提供内部取消能力，Netlify 路由只停止等待和后续阶段输出，不声称已终止网易云内部请求。其结束前仍可能占用资源。

### 接口兼容

`GET /api/music/song?id=<数字歌曲ID>` 保留 `audioUrl` 字段，增加可选 `errorCategory`。地址不存在保持 `200 + audioUrl:null + unavailable`；登录失效 401、上游/网络失败 502、超时 504、客户端取消 499、无效 ID 400。失败不缓存，响应使用 `Cache-Control: private, no-store`。请求 ID 仅接受 1–80 位字母、数字和连字符，否则重新生成。

## 测量记录与边界

- `loading-before.json`：优化前本地生产接口样本，歌曲 `29357087`，2 次地址请求，1 次成功取得地址；详情耗时 2,660 ms。封面 Node fetch 的 4 次请求均失败。保留原始失败样本，不剔除后只报告成功。
- `loading-after-initial.json`：首轮修改后同一首歌取地址 8,247 / 9 ms，两次均取得地址。关联 `measure-after-song-url-1` 的服务日志显示凭证准备约 2 ms、上游完成约 8,191 ms，等待主要在上游阶段。第二次很快不能直接归功于此次修改：检查到本地 NCM `server.js` 原有 `cache('2 minutes', …statusCode === 200)` 中间件，存在缓存影响；Netlify 直接 SDK 调用也不能套用这个结果。
- `loading-after.json`：再次测量同一首歌取地址 5,821 / 9 ms，两次均成功；详情 7,856 ms 后返回空歌曲数组，因此本轮没有可测的封面地址，不伪造封面结果。仍存在数秒的上游等待。早期探针两轮复用了 `measure-after-*` 标签，查看初轮时需同时限定 UTC `17:15:02–17:15:11`；测量脚本现已改为每轮 UUID，后续不会重用关联 ID。
- `cover-comparison.json`：同一张公共封面，通过 curl HTTPS 顺序比较，无浏览器缓存；原图首次下载在 12 秒限制内未完成（虽然 HTTP 为 200，但退出码 28，**不计成功**）；第二次完整下载 10,701 ms。96×96 两次完整下载为 5,826 / 3,731 ms。
- `cover-compare-0-2.jpg` 与 `cover-compare-96-2.jpg` 是同一封面的原图和缩略图证据。此前另一个封面的文件不作为这组体积对比依据。
- `node scripts/measure-loading.mjs before|after` 进行本地接口与封面 HTTP 测量，报告只保存脱敏状态与耗时，不下载音频、不写播放历史。再次运行同一标签会覆盖对应报告，归档时先另存文件。
- 首轮封面 Node 探针沿用了上游原始 HTTP 地址；脚本随后修正为缩略图使用与新界面相同的 HTTPS。初始探针失败不能当作新封面组件的加载结果。原图保留原始地址作对照，curl 的 HTTPS 同图对比另见 `cover-comparison.json`。
- 第一次/第二次仅表示该轮请求顺序，不代表已验证服务冷/热启动或浏览器缓存命中。网络未受控，不用少量样本证明优化因果或计算可靠 P90。后续相同歌曲、设备、网络的冷/热浏览器样本和弱网对比尚待采集。
