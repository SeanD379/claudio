# Netlify 扫码后歌单失败排查（本地修复，未部署）

> 2026-11-17 更新：已获用户授权完成正式发布，用户确认重新扫码后可以播放。本文“未部署”描述对应之前的本地排查阶段；当前部署 ID 和完整验收记录见 [上线记录](netlify-release-20261117.md)。

## 发现及证据

1. QR 模块将多条 `Set-Cookie`（包括重复的 Path、Expires、Max-Age）拼接后返回。应用原样将它装进一条 `nc_netease_session` Cookie。检查本地已有凭证，仅统计长度、不输出内容：原值 URL 编码后为 5,186 字节；去除响应属性并去重后为 1,110 字节。原值超过浏览器通常约 4KB 的单条 Cookie 限制：https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies 。
2. 本地文件能保存完整凭证，Netlify 则依赖数据库、实例缓存和浏览器 Cookie。浏览器拒收超长 Cookie 后，数据库不可达或请求落到另一实例，就可能出现“扫码成功，后续未登录”。这是与报告现象吻合的故障链；用户已提供线上网址并完成匿名接口复核，仍需扫码后的请求结果或函数日志确认本次线上触发条件。
3. `getValidCookie` 原先优先旧服务器缓存/数据库记录，当前浏览器新凭证仅作最后兜底。
4. 资料接口任何异常都返回空资料并删除服务端登录态；歌单接口部分上游错误返回成功的空列表；两个界面入口吞掉非 401 错误。因此无法区分未登录、服务故障和没有歌单。
5. 当前生产构建的 QR 和用户歌单依赖追踪完整，没有发现缺少 `user_playlist.js`；不据此声称过去部署一定完整。
6. 用户随后提供的报错是 **导入阶段** 的 404：`Failed to import from netease: Error: Playlist not found on Netease`。它对应 `POST /api/user/playlists` 获取详情返回空值的分支，不能继续将问题仅归于“我的歌单列表”接口。
7. 按 Netlify 冷启动条件设置全新临时目录，可稳定复现：临时匿名 token 不存在 → `util/request` 加载报 `ENOENT` → `getPlaylistDetail` 吞掉异常返回 `null` → 导入路由返回上述 404。此前仅 QR 的加载函数准备了该文件；另一个函数实例处理导入时不能依赖 QR 实例的临时文件。本地独立音乐服务会提前创建文件，掩盖了差异。此项是已复现的代码缺陷，但没有线上函数日志时仍不应宣称它是唯一触发原因。

## 本次修改

- 清理 Cookie 的响应属性和重复值，保留实际 Cookie 键值及值中的等号；在下发前限制编码长度，防止静默拒收。
- 请求携带的浏览器凭证优先，跳过不必要的凭证数据库读取。
- 资料服务暂时异常抛出可重试错误，不再删除登录态；确认凭证失效仍返回 401。
- 歌单服务异常返回 502，真正的空列表才返回 200；界面显示错误并提供重试。
- QR 和歌单成功响应明确禁用缓存；本地 HTTP 下 Cookie 不设置 Secure，HTTPS 保留 Secure、HttpOnly、SameSite=Lax。
- 断开连接清除浏览器 Cookie 和实例兜底；数据库不可达不阻止本地断开。
- `npm run build` 加入 NCM 依赖追踪检查，避免以后构建漏包被当成成功。
- 登录和歌单详情共用 `prepareNcmRuntime`，每个冷启动实例在加载请求模块前创建必要临时文件，保留已有匿名 token 内容。
- 歌单详情在本地和 Netlify 使用同一模块调用路径，并携带当前浏览器凭证；同步和详情 API 也传递凭证，防止仍依赖实例旧缓存。
- 详情请求仅在网易云明确返回 404 时按不存在处理；登录失效返回 401、权限不足返回 403、网络/模块/其他上游故障返回 502，并保留安全的上游状态码。获取详情失败时不创建歌单。
- 依赖追踪检查扩展到导入、同步和歌单详情接口。

## 2026-11-17 二维码生成失败的后续修复

用户随后反馈登录弹窗显示 `Client network socket disconnected before secure TLS connection was established`。对应新日志确认，失败发生在生成二维码时，用户尚未扫码；不能归咎于扫码操作，也没有证据认定 VPN 是根因。前轮的导入成功和页面验收不能证明整个登录链路已经稳定。

本次针对登录链路补充修复：

- 生成二维码和读取账号资料发生临时网络错误时，仅自动重试一次；明确鉴权错误、模块加载错误不重试，不涉及写入请求。
- 二维码 API 以 502 和简短提示表示服务连接失败，不再把内部 TLS 错误 JSON 发送给界面。两个登录入口也不再拼接 `detail` 字段。
- 绕开已安装 SDK 的 QR 错误分支中 `result` 未定义缺陷：保留明确的网络错误响应，不误报二维码过期。仅 800 表示过期，异常或缺失状态表示可重试的服务故障。
- 收到 803 但没有登录凭证时，不报告登录成功。
- 两个登录组件同一时间只保留一个轮询请求；刷新或关闭时取消旧浏览器请求，避免慢请求重叠和旧结果覆盖新二维码。查询暂时失败时保留二维码并提示重试。
- 新增的四项回归测试先复现失败，再修复通过；另覆盖异常状态与真正过期的区别。当前专项测试共 24 项通过，后端 ESLint 和类型检查通过。两个登录组件各有一条原有 `set-state-in-effect` lint 错误，本次未增加。

本次不改弹窗布局、系统代理、路由或 TLS 校验设置，仍未部署线上；临时文件和日志继续位于 D 盘。自动重试不等于消除外部网络故障，真实二维码显示和扫码仍需结合后续实测判断。

本次生产构建及部署依赖检查通过，预览已在原 3000 端口重启。真实调用 `/api/netease/login/qrcode?action=generate` 返回 200，存在二维码图片和 key，未返回内部 `detail`；响应为 `no-store, private`。此验证证明该次生成请求成功，不等于用户已扫码登录或外部网络已持续稳定。浏览器页面仍需刷新加载新代码。
